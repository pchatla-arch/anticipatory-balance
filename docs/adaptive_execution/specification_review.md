# Review of the Fleet Robust Execution attachment

The attachment provides a useful fixed system boundary and a concrete implementation narrative. Keep its execution-layer architecture and treat it as the organizing specification for the detailed paper. The changes below tighten claims, align the specification with current code, and make the experiments capable of validating the intended component.

| Attachment statement | Concrete correction |
|---|---|
| A fleet runs one policy; actuator mismatch is outside what the policy tolerates | Describe fleet variation as the deployment motivation. Lack of actuator randomization establishes a training-distribution difference, not demonstrated intolerance. The first experiment measures whether the existing policy actually degrades. |
| Retraining per robot does not scale; the fix has to sit between policy and motors | State the engineering objective: reduce repeated policy training and preserve a common policy interface. Compare cost and performance against actuator-randomized PPO. Neither the scaling limit nor the necessity of this placement has been established. |
| Everything inside the shaded boundary is designed and implemented | Replace with “This project specifies and will implement the components inside the boundary.” Add an evidence table: frozen actor/gain fault/privileged corrector/protocol implemented and CPU-checked; calibration, online estimation, confidence supervisor, C++ runtime and GPU recovery proposed or unverified. |
| A validated component | Use “a component to be validated against the stated protocol.” A simulation-only component can be validated within simulation assumptions after the experiments; current implementation checks are not the final capability evidence. |
| Per-joint gain, delay, saturation, friction and noise are the initial fault suite | Preserve them as staged test families. The implemented first gate changes proportional gain on the twelve leg actuators; it does not inject all listed families. Gain inversion is not a compensator for delay, friction or lost torque capacity. |
| Standing excitation identifies every joint in seconds | Present calibration duration and recoverability as measurements. Validate healthy standing and excitation first. Joint coupling, low excitation, saturation and sensor semantics may prevent per-joint identification; do not promise convergence time. |
| Freeze estimator updates whenever a foot is in contact | Treat contact-aware data selection as a proposed ablation. Contact does not automatically invalidate an actuator-force equation, nor does swing automatically remove all disturbance. Whole-robot contact freezing can suppress almost all learning while walking. Specify per-leg eligibility, effective information and update duty cycle. |
| Confidence follows covariance and prediction-error jumps | Label raw RLS covariance as an uncertainty proxy unless calibrated under the observation model. Add excitation, timestamp validity and model-mismatch checks; test coverage and false compensation rather than assuming confidence is reliable. |
| Safety supervisor falls back to the uncorrected controller | Call it a bounds and fault supervisor. Reverting to the base policy under a fault is not a safety guarantee. Define fault flags and any task-level response, then test that response. |
| Fixed-memory, fixed-time 1 kHz C++ | Keep C++ as a deliverable. First match the existing 50 Hz algorithm and 500 Hz physics timing. A 1 kHz adapter is a separately specified execution mode; evaluating it needs appropriate plant integration or a clearly labeled trace replay. Report measured tail latency, scheduling conditions and deadline misses. Hard real-time guarantees require more than a fast mean or a heap-free implementation. |
| Paired replayed episodes | Replay exogenous scenarios, initial states, commands, faults and stochastic inputs. Each controller must produce its own state trajectory. Replaying the reference robot states would remove the feedback behavior being evaluated. |
| If the first gate fails, switch to manipulation | Remove the automatic theme switch. A failed gate triggers the declared diagnostic and project checkpoint: distinguish interface/numerical invalidity, an already robust walker, insufficient correction authority and unsupported model assumptions. Preserve all tested settings and revise the protocol transparently if a specific defect is found. |
| Healthy performance does not regress beyond noise | Predeclare practical noninferiority margins and uncertainty intervals. Failure to detect a statistically significant difference does not establish non-regression. |
| RMA and residual adaptation 2026 are sufficient prior-work references | Include RL2AC, SAG, SG-CPG, TeAR, TAM, SPI-Active and Contact-UAN with their actual placement and information differences. Keep the component-building objective; state a specific conditional research contribution. |

## Correction law and timing

Use separate symbols for physical gain and correction authority, for example physical gain `g` and confidence weight `a`. Define the nominal physically clipped target `r`, candidate correction `d* = (1/g_hat - 1)(r-q)`, requested bounded/slew-limited correction `d`, and actual sent target. The attachment currently writes a bound on the derivative of the entire target, while the implemented code limits the rate of the correction. These are different constraints. Preserve the implementation's correction-rate statement unless total-target rate limiting is deliberately added and tested; clipping may change the effective correction faster than its requested slew limit.

The oracle is a specified bounded controller with privileged parameters. It is not an optimal controller or a universal performance upper bound. The planned online recovery fraction can be `(J_uncorrected - J_online)/(J_uncorrected - J_oracle)` for a lower-is-better loss, but only when the denominator is positive and meaningfully separated from zero. Report absolute effects, failure rates, and uncertainty alongside this ratio.

## Required early experiments

First retain the current gain-only feasibility protocol. Next test the allowed measurement interface with exact effort, explicitly noisy/delayed effort, and no effort. Include healthy-actuator contact/load changes to expose incorrect adaptation. Only after useful identification is shown should the plan expand to heterogeneous gains, gradual drift, a distinct dynamic-response family, and task transitions. The attached dates are a work plan rather than evidence that the modules already exist; use stage dependencies and paid-run budgets to manage execution.
